# Exploratory testing report — InstantLaTeX (pass 2)

Date: 2026-09-10 · Commit under test: `0877986` (master, clean)
Build: static site served from a scratch copy of `public_html/` via `python3 -m http.server 8642` (site root also contained two scratch host pages, `host.html` and `host-x.html`, used for embed tests). KaTeX 0.16.9 loaded from jsDelivr CDN (network available; Google Ads request returned 400 in this environment).
Driver: headless Google Chrome via puppeteer-core (`drive.js` in `/tmp/ilx-x2`, scenario files `r2-*` in this directory — copies committed here). Fresh browser profile per run.
Evidence: screenshots, console logs, and scenario scripts in this directory (`r2-*`).

Scope note: prior passes (REPORT.md, cgpt-evidence) covered hash round-trip fuzzing, the auto-pair bug family (#14, #15, #16), and edge hashes. This pass targeted the recently fixed auto-pair code under real keyboard use, the **never-explored iframe-embedding path**, and mobile viewport — the areas the previous report left unexplored.

## Journeys exercised

### Journey 1 — Type a formula by hand, correct it, undo, share via URL hash (against the fixed auto-pair code)
- Ordinary path: hand-typed `(x` then `)` → editor shows `(x)` (skip-over fix works); continued `+y)` → `(x)+y)`; full hand-typed quadratic `\frac{-b\pm\sqrt{b^2-4ac}}{2a}` produced **exactly** the default formula and rendered with no KaTeX error (`r2-j1-typing-11-4-hand-typed-quadratic.png`, console log). **Pass.**
- Variation (correction): Backspace after a typed pair deletes only the closer as expected; the pair-delete path (`Backspace` between an empty pair) removes both chars and is undoable via `execCommand('undo')` (`r2-undo-app-console.log`). **Pass.**
- Selection wrap via real keyboard (shift-select `abc`, type `(`) → `(abc)` with selection preserved inside the pair. **Pass.**
- Hash round-trip: reopening the app-written hash in a fresh tab restores value and render. **Pass.**
- Rejected candidate: synthesized **Cmd+Z did nothing** after edits — a control experiment on a plain `<textarea>` (`r2-undo-control-console.log`) shows headless Chrome does not perform native undo via synthesized keystrokes at all, while `execCommand('undo')` works. Driver limitation, not an app bug. Undo was re-verified with the validated `execCommand('undo')` probe instead: auto-pair insert, redo, and pair-delete are all undoable — the #15 fix holds.

### Journey 2 — Embed the editor in a host page (the previously unexplored `window.parent` path)
- Same-origin embed (`host.html` iframing `./index.html`): typing inside the iframe writes the shareable hash to the **parent** URL via `replaceState` (no history pollution: `history.length` 2→2); an externally edited parent hash syncs the editor; parent reload restores from hash; parent Back re-syncs via `hashchange`. This is the designed behaviour and it works. **Pass** (`r2-j2-iframe-sameorigin-console.log`).
- Cross-origin embed (`host-x.html` on `127.0.0.1` iframing `http://localhost:8642/index.html`): **CONFIRMED BUG — see below.** First attempt at this scenario was invalidated by a driver mistake (relative iframe `src` resolved same-origin); the genuine cross-origin run is `r2-j2-repro3.js` / `r2-j2-confirm.js` with the `r2-j2x-*` and `r2-j2final-*` screenshots.

### Journey 3 — Mobile viewport (375×667, DPR 2, touch, iPhone UA)
- No horizontal overflow (`scrollWidth` 375 = `innerWidth`); editor and output both visible and reachable; tap-focus and typing work; preview updates; hash is written. KaTeX errors render gracefully inline (red partial output). Desktop 800px also has no overflow. **Pass** (`r2-j3-mobile-*.png`).

## Confirmed bug

### BUG-2: Typing in a cross-origin embedded instance navigates the host page away entirely

**Status: CONFIRMED — reproduced 3× from fresh starting states (`r2-j2-repro3.js`, runs 1–3) plus final confirmation (`r2-j2-confirm.js`) and a no-app control (`r2-j2-control.js`). Filed as GitHub issue.**

User impact: any site that embeds InstantLaTeX in an iframe from a different origin (the exact scenario the `window.parent` targeting in `main.js` exists for, e.g. embedding `jonbaldie.github.io/InstantLaTeX` on another domain) loses its page the moment a visitor types a character in the embedded editor. The **top-level page navigates to the InstantLaTeX URL with the formula hash**, the host page is replaced in session history (pressing Back goes to `about:blank`, not the host page), and the visitor's place on the host site is destroyed.

Starting conditions: host page `http://127.0.0.1:8642/host-x.html` containing `<iframe src="http://localhost:8642/index.html">` (different origin). App at commit `0877986`.

Replay steps:
1. Load the host page; focus the editor inside the iframe.
2. Type any character (e.g. `x`) and wait ~700 ms (300 ms debounce).

Expected: the host page stays put; at most the iframe's own state changes.
Actual: the **top-level page navigates to `http://localhost:8642/index.html#x…`** — title changes from the host's to "Instant LaTeX", `history.length` becomes 2, and Back returns to `about:blank` (host page not in history). Screenshots `r2-j2final-1-before.png` (host) → `r2-j2final-2-after.png` (app replaced host) → `r2-j2final-3-back.png`.

Root-cause chain (observed + isolated by control):
1. `getUrlTarget()` (`main.js:34–43`) returns `window.parent`: the truthiness check `window.parent.location` does **not** throw cross-origin.
2. `urlTarget.history.replaceState(...)` throws `SecurityError` cross-origin (verified in control) → caught → falls through to `main.js:106–112`.
3. `urlTarget.location.replace(encodedHash)` — `Location.replace` is **allowed** cross-origin, and Chrome resolves the fragment-only URL against the *calling* context: the top page navigates wholesale to the app's origin. Control experiment (no app code): `parent.location.replace('#ctrltest')` from the cross-origin iframe turned the top page into `http://localhost:8642/index.html#ctrltest`.

So the fallback meant for "History API unavailable" fires on cross-origin *reads* being blocked and then performs an operation cross-origin code *can* perform — with the worst possible effect. Same-origin embeds are unaffected (`replaceState` succeeds there).

## Rejected candidates
- Synthesized Cmd+Z no-op — headless driver limitation (control: plain textarea behaves identically); app undo verified via `execCommand('undo')`.
- favicon.ico 404 on every load — cosmetic console noise, no functional impact; noted as a usability observation.
- Google Ads request 400 / blank ad slot in headless — ad-environment artifact; the DigitalOcean fallback did not trigger because `ins.children.length === 1` even though the ad rendered blank in this environment. The fallback's "filled" test is racy in principle (blank-but-present ad defeats it), but this could not be reproduced under ordinary conditions — unresolved observation, not filed.

## Unresolved candidates
- Ad-fallback trigger condition (`ins.children.length === 0` at `load`) can miss a blank-but-mounted ad slot; only observable when the ad network returns an empty creative. Not reproduced in an ordinary setup.

## Blocked / unexplored
- True mobile Safari behaviour (visual viewport, keyboard overlap) — only emulated device metrics in headless Chrome were exercised.
- Native Cmd+Z / Cmd+Shift+Z chords on the live site — unverifiable in this headless environment (see rejected candidate); the execCommand-based probes cover the same code path.

## Limitations
- The app was served from a scratch copy (plus two scratch host pages) rather than the repo checkout directly; content is identical (`public_html/` copied unmodified at commit `0877986`).
- Google Analytics/ads requests went to the live network; ads behaviour is environment-dependent as noted.
- Cross-origin embed testing used `localhost` vs `127.0.0.1` as distinct origins; OOPIF frame access needed retry wrappers (`r2-j2-repro3.js`).
